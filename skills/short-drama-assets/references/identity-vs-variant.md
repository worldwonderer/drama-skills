# 身份、变体与复用判断

## 三层问题

不要先问“要不要新建文件”，按顺序问：

1. **持续身份是否相同？** 换掉临时状态后，人物/空间/物体仍是不是同一个？
2. **下游是否需要区分一个可复用状态？** 变化会持续、再次出现，或影响参考图、
   分镜 binding、连续性吗？
3. **若不建变体，delta 是否足够？** 一瞬的动作、姿势、表情、相机角度通常交给
   occurrence/continuity/shot，不制造资产组合爆炸。

结果只能是 `reuse`、`new_variant`、`new_asset`、`unresolved`。
**`structural_invariant`：** 不能用“已处理”代替这四类，也不能让未决项带一个假 ID
流入下游。

## 持续锚点与可变状态

| 类别 | 持续身份通常由什么区分 | 通常属于变体/状态 | 通常不建变体 |
|---|---|---|---|
| Character | 同一人物、稳定面部/体态/永久特征、叙事身份 | 服装、发型整理、妆容、伤势、污湿、年龄阶段、伪装 | 瞬时表情、姿势、视线、景别 |
| Location | 同一空间地理、分区关系、入口、固定锚点、主要材料 | 可复用方向/View、陈设阶段、时段、天气、光态 | 单一镜头角度、焦段、演员站位 |
| Prop | 同一物件或同一可复用型号的形制、尺度、材料、功能、唯一标记 | 所有者/手/位置、开闭、破损、内容物、文字、启停 | 被抬起的一瞬、画面左右位置 |

这张表是 **`craft_default`**，不是见词建档的公式。变化是否值得成为 variant 取决于
持续时间、重复使用、故事辨识度和下游绑定需求。

## 决策阶梯

### A. 先排除“只是镜头事实”

“侧脸”“从背后看”“俯拍柜台”“杯子在画面右侧”不改变资产。若只在一个镜头的
一瞬成立，交给 storyboard boundary/keyframe。

### B. 寻找同一身份的证据

用已有 ID 的稳定锚点、剧情连续、来源/去向和唯一标记对齐；不要只按显示名。两个都
叫“值班员”的人不因此相同，同一人换了称谓也不因此不同。

### C. 判断变化是否应成为变体

同时问：

- 有明确 cause/source 吗？例如换装、受伤、停电、拆封、转交。
- 有清楚 validity 吗？从哪个 block/scene/episode 生效，到何时失效或未知。
- 下游需要精确选择吗？若角色带伤跨三场，Look 值得建；手指刚沾一滴水又擦掉，
  delta 可能足够。
- 它能否独立描述而不篡改 base？变体写差异，不重写成另一个身份。

同一 `looks.jsonl`/`location-views.jsonl` 内的 base 关系分别写
`base_look_id`/`base_view_id`。只有 base 在另一个 artifact 时才使用 canonical
`base_ref`；禁止让记录引用包含自身的文件 hash。

### D. 只有持续身份不同才建新 asset

- 剧本确认是另一个人，即使穿着相同；
- 空间拥有不同地理/入口/固定锚点，即使同属一个建筑；
- 两件需独立追踪的同款物件，或形制/功能/材料身份真正不同。

若证据不足，选择 `unresolved` 而不是靠常识补齐。

## 容易误判的情形

### 年龄、替身、伪装

- 同一人物的少年/成年阶段通常是不同 Look；若制作上由不同演员且身份匹配策略不同，
  仍保持一个 Character，可在 Look 中写表演/演员约束。
- 剧情中的“双胞胎”“复制体”“冒名者”是不同 Character，即使视觉锚点近似。
- 易容或制服伪装是 Look，不把“伪装身份”写成真实 Character；若观众暂时未知，
  可限制显示名，不能破坏内部 truth。

### 同址空间

“渡站大厅”和“渡站值班室”若有各自可生产的地理与入口，适合两个 Location，并用
关系指针连接；不是把整个建筑所有房间塞进 Views。相反，同一值班室停电前后仍是
同一 Location，不因光态变化新建地点。

### 同款多件道具

两枚外观相同、分别由不同角色保管且会被交换的号牌，需要两个 Prop 身份；“十只
无连续性要求的白杯”可以是一类 set dressing occurrence。是否个体化由叙事追踪决定，
不由外观相似决定。

### 损坏与改造

裂纹、血迹、装入文件通常是 State；若物体被不可逆改造成另一功能（门牌被熔成钥匙）
且之后按新物件使用，可提议新 asset 并保留 derived-from 关系。该边界需 creator 接受。

## 合成判断例

已有 `CHAR-GUHE` 与 `LOOK-GUHE-WORK`。本集顾禾套上橙色雨衣进入渡站，第三场
雨衣右肩被淋湿。

- 橙色雨衣会跨两场并用于参考图：`new_variant`，base 为 Character，不是新角色；
- 右肩湿痕只持续半场：先写 continuity delta，不必自动生成第三个 Look；
- 若下一集仍需精确复现湿痕并绑定参考图，再由 creator 接受一个 wet Look variant。

若文本只写“穿橙雨衣的人”，且无法证明就是顾禾：decision 必须 `unresolved`。

## 决定记录应能解释取舍

每条 decision 至少展示 source occurrence、候选、选择、稳定证据、差异、cause、
validity、下游影响和 creator acceptance。`new_asset` 要说为什么不能复用；
`new_variant` 要说 base 什么不变；`reuse` 要说现有 variant 如何覆盖本次事实。

接受前字段只叫 `proposed_binding`。只有 `creator_acceptance.status=accepted`
且对应 bible identity/variant 已发布后，发布交易才能生成 `accepted_binding`。
下游只读后者；不得因 ID 已经长得像正式 ID，就把 proposed 记录当 accepted。

**`reviewed_invariant` AST-04：** reviewer 检查身份锚点与临时状态有没有混写，而不
以“资产越少越好”作为评价标准。

## 生产实践印证

完整生产链的定性案例显示，这种拆分能减少换装、伤势与视角变化导致的重复资产，
可作为命名与拆分的 `craft_default` 参照（示例为合成改写）：

- **变体后缀命名**：同一人物的不同状态/造型用后缀区分——状态轴如
  “苏某-火灾后无伤”，造型轴如“祁某：红色修身礼服”。身份名在前、变体在后，
  下游 binding 一眼可读。
- **空间按朝向拆 View**：同一地点按朝向/分区命名可复用视图——“医院走廊（北）”
  “办公室（东）”，与 Location/View 拆分（AST-03）完全对应；每个 View 单独绑定
  参考图。
- **角色元数据轴**：性别、年龄段（少年/青年/中年/老年）、类别是生产端稳定
  追踪的识别字段；年龄段跨越（少年→成年）在生产中确以不同 Look 处理。
- **参考图绑定纪律**：每个出镜实体（人物与空间）在下游提示词中逐一绑定
  参考图；无绑定的“路人若干”按 set dressing occurrence 处理，不建身份。
- **命名分层**：主角实名；功能角色姓+职务（李校长/陈秘书）；龙套类型+甲乙丙
  （首选）或 ABC；非人角色类别直称（魔物甲/虎妖）。资产名与描述内名字必须
  一致——“写 A 名生成 B 人”是真实返工事故。
- **大状态直接开新 Look**：被俘/重伤等会持续多集的大状态，生产端直接固化进
  新定妆图（“胸口与手臂有绳索捆绑勒痕”），不靠下游合成硬改——与本文“若下一集
  仍需精确复现再建 variant”的阶梯一致，只是量产剧倾向提前建。
